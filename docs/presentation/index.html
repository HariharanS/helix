Helix

A multi-agent orchestration system that drives a feature from intent to production across multiple repositories.
Built on GitHub Copilot CLI · tech-agnostic by design

01What Helix is

A workspace hub of agents, skills, prompts, hooks, and traces that turn a fuzzy idea into a merged change — without you driving each step yourself.

Orchestrator

One helix agent routes work to specialised sub-agents (jam, architect, decomposer, implementer, reviewer, distiller, ui-tester) based on the active workflow and phase.

Workspace-scoped

Each feature lives in workspaces/{id}/ with its own PRD, tech-design, slices, mental model, and trace history. Multiple workspaces coexist in one meta-repo.

Native Copilot files

Uses .github/agents/, .github/skills/, .github/prompts/, .github/hooks/. No bespoke runtime — everything is markdown plus small Node scripts.

Cross-repo aware

A single workspace can span N sub-repos. Slices declare repos, cross_repo_contracts, and topological ordering over the contract graph.

Captures every session

Each session emits a derived trace at sessionEnd. Traces feed eval, distillation, and the operator's labelled corpus.

Tech-agnostic core

No language, framework, or transport baked in. Verification commands are operator-supplied opaque strings; example stacks (.NET on AWS) are illustrative only.

02Install flow

Two scripts. The first turns a directory into a Helix meta-repo; the second wires up a feature workspace and pulls the participating sub-repos.

1

Initialise the meta-repo

Lays down agents, skills, prompts, hooks, templates, and the registry stub. By default also bootstraps a CRG (code-review-graph) MCP context provider.

pwsh helix/scripts/init-meta-repo.ps1
  # flags: -SkipCRG, -SkipDoctor, -Force
2

Edit helix-repos.yml

Declare the registry of sub-repos (id, remote, local_path) the meta-repo can pull from. Placeholders block setup until replaced.

3

Set up a workspace

Per-workspace: clones or fetches the participating sub-repos under workspaces/{ws}/repos/*, seeds an empty mental-model.md, builds the CRG graph for each repo when mode: mcp, and seeds verification policy.

pwsh helix/scripts/setup-workspace.ps1 -Workspace feature-orders-events
  # flags: -CloneMissing, -FetchExisting, -SkipGraphBuild
Sub-repos are separate git repos. Helix does not install per-repo git hooks — everything reactive lives in Copilot CLI lifecycle hooks under helix/.github/hooks/.

04Skill discovery & promotion

When Helix attaches to a repo, repo-local skills under .github/skills/ become discoverable to that workspace. Skills used across teams promote upward through a four-rung destination taxonomy.

rung 1

repo

Lives in the sub-repo's .github/skills/. Discoverable only when that repo is part of an active workspace. Owned by the repo team.

rung 2

workspace / meta

Lives in the meta-repo's .github/skills/. Available to every workspace under that meta-repo. Owned by the operator running Helix.

rung 3

helix-core

Promoted into Helix itself when a pattern shows up across multiple meta-repos / teams. Ships with Helix; benefits everyone who installs.

rung 4

personal

Operator's home directory — idiosyncratic preferences that should not bleed into team-shared rungs.

Promotion gate

A candidate promotes only when all are true: occurrences ≥ 3 · features ≥ 2 (distinct) · held_out_replay = PASS · quarterly_promotions < 5 (hard cap). Even when eligible, the distiller writes Recommendation: CREATE SKILL and stops — the operator runs /hc-maker.

Operator-signed-off Evidence accumulates across features, not per-session

Source: helix/docs/distillation-architecture.md · Persistence: .helix/skills/{candidates,graveyard,audits}/

05Skill improvement over time

Skills are not static. Three operator-driven prompts manage the lifecycle. Helix never auto-promotes or auto-graveyards.

/hc-distill

Runs the hc-distiller agent against the active session. Appends evidence to existing candidates instead of duplicating; checks the graveyard fingerprint before suggesting a candidate.

/hc-skill-audit

Quarterly roll-up. Reads candidates/, graveyard/, and usage.jsonl; writes audits/{YYYY-Q#}.md with promotions made, graveyards, and edit-distance trend.

/hc-skill-graveyard <id>

Operator rejects a candidate with reason + a fingerprint to suppress re-suggestion. Idempotent. The candidate file is deleted; full evidence remains in git history.

Honest gap — deferred

Edit-distance feedback writer is not built. The schema for usage.jsonl ships, including an edit_distance field, but no agent or hook writes it. Three approaches were considered (hook-based, skill-side append, operator command); all were rejected as either noisy (load ≠ use) or unreliable. The right time to ship a writer is when an operator first asks “I keep editing skill X the same way — can we just demote it?”

/hc-skill-audit already skips the edit-distance section gracefully when usage.jsonl is empty.

06Eval & quality

The plan originally called for nine designed scenarios + a Week-6 baseline comparison. With one real (uncommittable) workspace and zero committed runs, that would have measured imagination, not Helix. So eval was reframed into two layers.

Layer 1 — Regression

Pure unit tests against hook scripts and runtime helpers. No Copilot CLI, no LLM, no network. Catches plumbing breakage with a single correct answer.

86 tests, all green

  • pre-tool-use dangerous-command gate
  • helix-runtime redact / truncate / sanitize / parseSimpleYaml
  • derive-trace kind mapping, latency math, nested subagent attribution
  • distill-trigger, label schema, skill-persistence, mental-model

Run with node --test helix/evals/regression/*.test.js

Layer 2 — Quality baseline

Every real Helix session emits a trace at sessionEnd. The operator labels each via /hc-label-session, writing a sibling .label.yml with three required fields:

correctnessmatch | partial | wrong
reworknone | minor | major
notessingle-line free-form

Corpus is empty today

Promotion to “golden scenarios” in helix/evals/golden/ waits for ≥20 labelled traces across ≥3 distinct workspaces, including ≥1 cross-repo. Estimated Week 12+.

07Cross-repo mental model

Some coupling between repos cannot be auto-derived — shared terms, feature-flag inventory, behavioural conditions, divergence between “what we said” and “what shipped.” workspaces/{ws}/mental-model.md captures it.

Six fixed sections

  1. Domain Glossary
  2. Flag Inventory
  3. Coupling Map
  4. Behavior Conditions
  5. State Diagrams
  6. Surprise Log append-only

Architect owns sections 1–5 and updates them during tech-design. Operator and implementer append to the Surprise Log via /hc-surprise.

/hc-surprise — divergence capture

Asks for title, expected, actual, optional repos. Appends a dated ### YYYY-MM-DD — title entry under ## Surprise Log.

### 2026-04-29 — orders-api emits
       OrderPlaced.v1 but worker
       subscribes to v0

**Expected:** Coupling map said v1 both sides
**Actual:**   worker hard-codes v0
**Repos:**    orders-api, orders-worker

Path taken: defer auto-population

Static analysis to auto-populate Flag Inventory and Coupling Map was the original plan. Useful detection requires stack-specific patterns (env-var conventions, framework-specific HTTP-route attributes, event-publish APIs) — that violates Helix's tech-agnostic constraint. Section names are forward-compatible with whichever later path lands. The right signal to revisit is “the same kind of surprise has shown up three times in two workspaces.”
